# 代码审计策略

## 1. 审计目标

对校园充电桩管理系统进行全面代码审计，识别安全漏洞、代码质量问题、性能瓶颈和技术债务，为后续修复提供优先级排序的路线图。

## 3. 风险等级定义

### P0 — 立即修复（Critical）

定义：可直接导致安全入侵、数据泄露、系统崩溃或业务中断的问题。

判定标准：
- 可被外部攻击者利用的安全漏洞
- 认证/授权完全缺失或可绕过
- 敏感数据以明文形式持久化或传输
- 系统关键功能在正常使用下必然崩溃
- 存在远程代码执行或 SQL 注入风险

### P1 — 优先修复（High）

定义：严重影响性能、核心业务流程正确性或长期可维护性的问题。

判定标准：
- 严重性能瓶颈（如全表扫描、N+1 查询）
- 核心业务逻辑错误
- 配置不当导致潜在安全风险
- 重要功能缺失或错误实现
- 测试覆盖率低于 20% 的核心模块

### P2 — 计划修复（Medium）

定义：代码质量问题和技术债，不影响当前功能但影响长期质量。

判定标准：
- 代码重复（超过 3 处重复）
- 类型安全问题（滥用 `any`、强制类型转换）
- 超长函数（>200 行）
- 未使用的组件/代码
- 不规范的分层设计
- 缺少必要的注释和文档

### P3 — 记录观察（Low）

定义：轻微规范问题、风格不一致、非关键优化建议。

判定标准：
- 命名规范轻微偏离
- CSS/样式冗余
- 注释不完整或过时
- 非关键性代码风格不一致

## 5. 审计方法

### 5.1 静态代码分析
- 逐行人工审查关键安全代码（认证、授权、输入处理）
- 模式匹配查找常见漏洞模式（SQL 拼接、硬编码密钥、路径遍历等）
- 架构层面评估分层设计和模块边界

### 5.2 配置审计
- 检查环境配置是否正确分离（dev/prod）
- 验证密钥和凭据是否硬编码
- 评估第三方依赖版本安全性

### 5.3 数据库审计
- 检查表结构设计和索引策略
- 分析 SQL 查询性能
- 评估数据完整性约束
