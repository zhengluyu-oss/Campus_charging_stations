# 实战开发工作手册

> 本手册说明三个场景的使用流程：接手新项目、开发新功能、代码审计。
> 每个步骤注明调用哪个技能、触发方式、产出文件位置。

---

## 技能触发方式说明

| 类型 | 触发方式 |
|------|---------|
| **Superpowers 技能** | AI 根据你描述的意图自动调用，无需输入命令 |
| **OpenSpec 技能** | 你输入斜杠命令显式触发（`/opsx:propose`、`/opsx:apply`、`/opsx:explore`、`/opsx:archive`） |

---

---

## 第一部分：接手新项目，建立完整认知

**目标：** 在不改动任何代码的前提下，建立对项目架构、模块、业务流程的完整认知。

**使用技能：** 只用 Superpowers，不需要 OpenSpec（此阶段只有分析，无代码变更）

---

### 步骤 1：探索整体架构

**调用技能：** `brainstorming`（Superpowers，AI 自动调用）

描述目标："帮我分析这个项目的整体架构，不要修改任何代码。"

AI 调用 `brainstorming` 后将：
- 扫描项目文件结构、核心代码、依赖关系
- 逐步向你确认理解（一次一个问题）
- 生成设计文档并自动保存

分析内容：技术栈、目录结构、核心模块、主要依赖、分层架构、模块依赖关系、调用链路、风险区域

**产出文件：**
```
docs/superpowers/specs/YYYY-MM-DD-项目架构-design.md
```

---

### 步骤 2：深入业务模块

**调用技能：** `brainstorming`（Superpowers，AI 自动调用）

描述目标："继续分析各个业务模块和核心业务流程。"

分析内容：每个模块的职责与核心文件、业务流程（用户流程、请求流程、数据流程）、状态流转、接口分类与权限体系

**产出文件：**
```
docs/superpowers/specs/YYYY-MM-DD-业务模块-design.md
```

---

### 步骤 3：分析数据与基础设施

**调用技能：** `brainstorming`（Superpowers，AI 自动调用）

描述目标："分析项目的数据库设计和基础设施，包括缓存、消息队列、第三方服务等。"

分析内容：核心表结构、表关系、索引设计、缓存策略、数据库、Redis、MQ、部署架构

**产出文件：**
```
docs/superpowers/specs/YYYY-MM-DD-数据基础设施-design.md
```

---

### 步骤 4（可选）：深挖某个具体模块

**调用技能：** `openspec-explore`（OpenSpec，斜杠命令调用）

**输入命令：**
```
/opsx:explore
```

进入探索模式后描述疑问。探索模式只读代码，不写代码，AI 追踪调用链、画 ASCII 架构图、比较方案，跟着你的思路走，没有固定流程和强制产出。

---

### 完成标准

```
docs/superpowers/specs/
├─ YYYY-MM-DD-项目架构-design.md
├─ YYYY-MM-DD-业务模块-design.md
└─ YYYY-MM-DD-数据基础设施-design.md
```

## 第二部分：开发新功能

**完整流程：**

```
① brainstorming     → ② /opsx:propose  → ③ writing-plans（自动衔接）
→ ④ using-git-worktrees（自动）  → ⑤ subagent-driven-development（自动）
→ ⑥ /opsx:explore（设计变更时）  → ⑦ requesting-code-review（自动）
→ ⑧ /opsx:archive  → ⑨ finishing-a-development-branch（自动）
```

---

### 步骤 1：需求探索与技术设计

**调用技能：** `brainstorming`（Superpowers，AI 自动调用）

描述目标："我要开发 XX 功能，帮我分析需求和技术方案，不要写代码。"

AI 调用 `brainstorming` 后将：
1. 扫描现有代码了解上下文
2. 一次一个问题逐步澄清需求
3. 提出 2-3 种技术方案供你选择
4. 你选定方案后，逐节展示设计，每节等你确认
5. 你批准后生成设计文档，提交 git

**产出文件：**
```
docs/superpowers/specs/YYYY-MM-DD-<功能名>-design.md
```

> `brainstorming` 硬性规则：设计文档未经你批准，禁止生成任何代码。

---

### 步骤 2：创建 OpenSpec 变更记录

**调用技能：** `openspec-propose`（OpenSpec，斜杠命令调用）

**输入命令：**
```
/opsx:propose <变更名>
```

AI 调用 `openspec-propose` 后将：
1. 运行 `openspec new change "<变更名>"` 创建目录
2. 按依赖顺序生成 proposal.md → design.md → tasks.md
3. 展示最终状态

**产出文件：**
```
openspec/changes/<变更名>/
├─ proposal.md    ← 为什么做（背景、目标、影响范围）
├─ design.md      ← 怎么做（设计决策、权衡、迁移计划）
└─ tasks.md       ← 任务清单（- [ ] 待做项）
```

---

### 步骤 3：编写实施计划

**调用技能：** `writing-plans`（Superpowers，由 `brainstorming` 自动衔接调用）

步骤 1 你批准设计文档后，AI 自动进入 `writing-plans`，无需单独触发。

**产出文件：**
```
docs/superpowers/plans/YYYY-MM-DD-<变更名>.md
```

计划包含：每个任务的精确文件路径、具体代码、测试命令、预期输出，遵循 TDD 节奏。

计划生成后，AI 询问执行方式，选择"子代理驱动"进入步骤 5。

---

### 步骤 4：创建隔离工作区

**调用技能：** `using-git-worktrees`（Superpowers，执行开发前 AI 自动调用）

AI 调用此技能后将：
1. 检测是否已在隔离工作区（已在则跳过）
2. 创建 `.worktrees/<变更名>/` 工作区
3. 安装项目依赖
4. 运行测试确认基线干净

---

### 步骤 5：执行开发任务

**调用技能：** `subagent-driven-development`（Superpowers，你选择执行方式后 AI 自动调用）

每个任务的内部流程（AI 自动完成）：
1. 派遣实现子代理 → 按 TDD 实现代码，自检提交
2. 派遣规格审查子代理 → 确认代码符合 design.md 规格，不符合则修复后再审
3. 派遣代码质量审查子代理 → 检查代码质量，有问题则修复后再审
4. 通过后标记任务完成，同步将 `tasks.md` 中 `- [ ]` 改为 `- [x]`
5. 进入下一个任务，直到全部完成
6. 全部完成后派遣最终审查子代理，然后自动调用 `finishing-a-development-branch`

---

### 步骤 6：开发过程中出现设计变更时同步文档

**调用技能：** `openspec-explore`（OpenSpec，斜杠命令调用）

**输入命令：**
```
/opsx:explore <变更名>
```

进入探索模式后描述发现的问题。探索模式会：
- 读取当前变更的所有文档
- 分析方案变更的影响
- 提议更新哪个文档的哪个部分（不自动修改，等你确认）

**文档更新位置：**

| 变更类型 | 更新到 |
|---------|-------|
| 发现新需求 | `openspec/changes/<变更名>/specs/<模块>/spec.md` |
| 设计决策改变 | `openspec/changes/<变更名>/design.md` |
| 任务范围变化 | `openspec/changes/<变更名>/proposal.md` |
| 新增任务 | `openspec/changes/<变更名>/tasks.md` |

---

### 步骤 7：开发完成后代码复审

**调用技能：** `requesting-code-review`（Superpowers，AI 自动调用）

描述目标："所有任务已完成，帮我进行代码复审，复审报告保存到变更记录文件夹。"

AI 调用此技能后将：
1. 获取本次变更的 git commit 范围
2. 派遣代码审查子代理（提供功能描述、计划文档、commit 范围）
3. 生成结构化审查报告

**复审报告保存到：**
```
openspec/changes/<变更名>/review.md
```

报告内容：代码亮点、Critical 问题、Important 问题、Minor 问题、整体评估

收到报告后，AI 自动调用 `receiving-code-review` 处理反馈：
- 不清楚的先澄清，不猜测就实现
- 按优先级处理：Critical → Important → Minor
- 每修复一项运行测试验证

---

### 步骤 8：归档变更记录

**调用技能：** `openspec-archive-change`（OpenSpec，斜杠命令调用）

**输入命令：**
```
/opsx:archive <变更名>
```

AI 调用此技能后将：
1. 确认所有任务已打钩（`- [x]`）
2. 检查是否有规格变更需要同步
3. 移动变更目录到归档位置（加日期前缀）

**归档后位置：**
```
openspec/changes/archive/YYYY-MM-DD-<变更名>/
├─ proposal.md
├─ design.md
├─ tasks.md       ← 全部 - [x]
└─ review.md      ← 复审报告
```

---

### 步骤 9：完成开发分支

**调用技能：** `finishing-a-development-branch`（Superpowers，由步骤 5 自动调用）

AI 调用此技能后将：
1. 运行测试套件（失败则停止）
2. 检测工作区状态
3. 展示选项等你选择：
   ```
   1. 合并到主分支（本地）
   2. 推送并创建 Pull Request
   3. 保留分支（之后手动处理）
   4. 丢弃这个分支
   ```

---

### 完整产出汇总

| 阶段 | 文件 | 位置 |
|------|------|------|
| 设计 | `YYYY-MM-DD-<功能名>-design.md` | `docs/superpowers/specs/` |
| 实施计划 | `YYYY-MM-DD-<变更名>.md` | `docs/superpowers/plans/` |
| 变更提案 | `proposal.md` | `openspec/changes/<变更名>/` |
| 设计决策 | `design.md` | `openspec/changes/<变更名>/` |
| 任务清单 | `tasks.md` | `openspec/changes/<变更名>/` |
| 复审报告 | `review.md` | `openspec/changes/<变更名>/` |
| 归档 | 以上所有文件 | `openspec/changes/archive/YYYY-MM-DD-<变更名>/` |

## 第三部分：代码审计，查找 Bug

**目标：** 全面扫描代码库，发现 Bug、安全漏洞、性能问题、技术债，输出可执行的修复路线图。

**使用技能：** 只用 Superpowers，不需要 OpenSpec（此阶段只有分析，无代码变更）

发现问题后如需修复，每个修复作为独立 OpenSpec 变更，走第二部分流程。

---

### 步骤 1：制定审计策略

**调用技能：** `brainstorming`（Superpowers，AI 自动调用）

描述目标："帮我对整个项目进行代码审计，先制定审计策略，不要修改任何代码。"

产出内容：审计范围与优先级、风险分类维度（Critical / High / Medium / Low）、审计路线图

**产出文件：**
```
docs/superpowers/specs/YYYY-MM-DD-审计策略-design.md
```

---

### 步骤 2：代码质量审计

**调用技能：** `brainstorming`（Superpowers，AI 自动调用）

描述目标："开始代码质量审计，检查架构设计、代码规范、测试覆盖等问题。"

检查内容：分层设计与模块边界、循环依赖、重复代码、超长函数、命名规范、代码复杂度、测试覆盖率、架构一致性

**产出文件：**
```
docs/superpowers/specs/YYYY-MM-DD-代码质量审计-design.md
```

---

### 步骤 3：安全审计

**调用技能：** `brainstorming`（Superpowers，AI 自动调用）

描述目标："进行安全审计，重点检查认证授权、输入校验和敏感数据处理。"

检查内容：
- **身份与访问控制：** Token 验证、Session 安全、权限绕过、越权风险
- **输入输出安全：** SQL Injection、XSS、CSRF、Path Traversal、SSRF
- **数据保护：** 硬编码密钥、敏感数据暴露、日志泄露

**产出文件：**
```
docs/superpowers/specs/YYYY-MM-DD-安全审计-design.md
```

---

### 步骤 4：性能审计

**调用技能：** `brainstorming`（Superpowers，AI 自动调用）

描述目标："进行性能审计，检查数据库查询、缓存使用和并发处理。"

检查内容：SQL 性能、N+1 查询、深分页、缓存策略、并发处理、内存占用

**产出文件：**
```
docs/superpowers/specs/YYYY-MM-DD-性能审计-design.md
```

---

### 步骤 5：依赖与技术债审计

**调用技能：** `brainstorming`（Superpowers，AI 自动调用）

描述目标："审计第三方依赖风险和技术债务情况。"

检查内容：第三方库版本、安全漏洞、过期依赖、技术债优先级与修复成本

**产出文件：**
```
docs/superpowers/specs/YYYY-MM-DD-依赖技术债审计-design.md
```

---

### 步骤 6：生成综合审计报告

**调用技能：** `brainstorming`（Superpowers，AI 自动调用）

描述目标："汇总所有审计结果，生成综合审计报告，按 P0/P1/P2/P3 优先级排序，给出修复路线图。"

报告优先级定义：
- **P0（立即修复）：** 安全漏洞、数据泄露风险、系统崩溃
- **P1（优先修复）：** 严重性能问题、核心业务风险
- **P2（计划修复）：** 代码质量问题、技术债
- **P3（记录备案）：** 轻微规范问题

**产出文件：**
```
docs/superpowers/specs/YYYY-MM-DD-综合审计报告-design.md
```

---

### 步骤 7：对具体 Bug 进行深度根因分析

**调用技能：** `systematic-debugging`（Superpowers，AI 自动调用）

描述目标："对这个 Bug（描述现象）进行根本原因分析，不要修改代码。"

AI 调用 `systematic-debugging` 后强制执行四阶段分析：

| 阶段 | 内容 |
|------|------|
| 1. 根本原因调查 | 读错误信息、复现问题、追踪数据流 |
| 2. 模式分析 | 找到类似能正常工作的代码，比较差异 |
| 3. 假设验证 | 提出单一假设，最小化验证，一次只改一处 |
| 4. 修复方案 | 提出最小化修复方案（此阶段不写代码） |

> 铁律：未完成根本原因调查，AI 不允许提出任何修复方案。

分析完成后如需实际修复，走第二部分流程，创建 `fix-<bug编号>` 变更记录。

## 快速索引

| 场景 | 调用技能 | 触发方式 |
|------|---------|---------|
| 接手项目：分析架构/模块/数据 | `brainstorming` | AI 自动（描述目标） |
| 接手项目：深挖某个模块 | `openspec-explore` | `/opsx:explore` |
| 开发新功能：需求分析与技术设计 | `brainstorming` | AI 自动（描述需求） |
| 开发新功能：创建变更记录 | `openspec-propose` | `/opsx:propose <变更名>` |
| 开发新功能：编写实施计划 | `writing-plans` | AI 自动（接在 brainstorming 后） |
| 开发新功能：执行开发 | `subagent-driven-development` | AI 自动（接在 writing-plans 后） |
| 开发中设计变更，同步文档 | `openspec-explore` | `/opsx:explore <变更名>` |
| 开发完成：代码复审 | `requesting-code-review` | AI 自动（描述"做复审"） |
| 开发完成：归档变更 | `openspec-archive-change` | `/opsx:archive <变更名>` |
| 代码审计：全项目扫描 | `brainstorming` | AI 自动（描述"做审计"） |
| 代码审计：具体 Bug 根因分析 | `systematic-debugging` | AI 自动（描述 Bug 现象） |
| 手动执行变更任务 | `openspec-apply-change` | `/opsx:apply <变更名>` |
