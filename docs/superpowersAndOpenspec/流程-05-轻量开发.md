# 流程 05：轻量开发（OpenSpec）

**目标：** 对低风险、小范围改动，用 OpenSpec 快速记账并执行，省略 Superpowers 完整质量链。

**前置：** 先阅读 [文档管理规范.md](文档管理规范.md)。

**适用：** 改动 ≤ 3 个文件、逻辑清晰、无架构决策、回滚容易。

**质量替代：** 跨模块、有架构决策、涉及安全/权限/金额/数据库/核心业务状态时，见 [流程-02-开发新功能.md](流程-02-开发新功能.md)（Superpowers 质量流程）。

**核心原则：** 本流程仅使用 OpenSpec，不创建 `superpowers/changes/` 设计链，避免与流程 02 形成两套 `plan.md` / `tasks.md`。

**分支原则：** 开发开始前，用户已经手动创建并切换到功能分支。AI 只在当前分支落代码，禁止自动创建新分支、切换分支或创建 git worktree；除非用户明确要求。

---

## 路径选择

| 条件 | 推荐流程 | 说明 |
|------|----------|------|
| 改动 ≤ 3 个文件 / 逻辑清晰 / 无架构决策 / 回滚容易 | **流程 05（本流程）** | OpenSpec：propose → apply → archive |
| 跨多模块 / 有架构决策 / 涉及安全、权限、金额、数据库、核心业务状态 | **流程 02** | Superpowers 全链路质量门禁 |

不确定时默认走流程 02。

---

## 流程概览

**目录命名：**

| 阶段 | 目录路径 | 示例 |
|------|----------|------|
| 进行中 | `openspec/changes/<序号>-<变更名>/` | `openspec/changes/7-fix-button-style/` |
| 已归档 | `openspec/changes/archive/YYYY-MM-DD-<序号>-<变更名>/` | `openspec/changes/archive/2026-07-08-7-fix-button-style/` |

**Git 规则：**

- **AI 文档不入 `.gitignore`**：`openspec/changes/`（含 `archive/`）不得加入 `.gitignore`，须对 git 可见。
- **逐任务提交（强制）**：每完成 `tasks.md` 中的一条任务，必须立即将**本任务功能代码**以**中文 commit 说明**提交到本地仓库；该次 commit **只包含功能代码**，不得 `git add` AI 文档。
- **中文 commit（强制）**：commit 描述必须使用**中文**；禁止使用英文作为主描述。
- **一任务一提交**：每个小任务对应一次独立 commit。
- **仅本地提交**：默认只 `git commit` 到本地仓库；**禁止**未经用户明确要求就 `git push` 到远程。
- **AI 文档提交**：是否、何时将 AI 文档单独 commit，由用户决定。

**执行依据：** `openspec/changes/<序号>-<变更名>/tasks.md`。

```
① /opsx:propose <序号>-<变更名>     → proposal.md + tasks.md
② 当前分支检查（可选基线验证）
③ /opsx:apply <序号>-<变更名>       → 按 tasks.md 逐条实现
④ /opsx:archive <序号>-<变更名>     → 归档至 openspec/changes/archive/
```

产出文件路径规范见 [文档管理规范.md](文档管理规范.md) 第 3.5–3.6 节。

## 步骤 1：创建变更

```
/opsx:propose <序号>-<变更名>
```

**调用技能：** `openspec-propose`（通过 `/opsx:propose` 触发）

产出 `proposal.md` + `tasks.md`。`tasks.md` 即为执行清单；每条任务须含**中文 commit 说明**（完成后用于本地提交）。

`proposal.md` 至少包含：变更动机、范围、影响面、验收方式。

---

## 步骤 2：确认当前分支（建议）

**调用方式：** 普通 git 状态检查

- 确认当前分支不是 `main` / `master` / 受保护发布分支。
- 记录当前分支名。
- 检查工作区未提交改动，区分用户已有改动与本次范围。
- 对改动涉及模块跑快速基线（构建 / 相关测试）；基线失败时报告并询问是否继续。

---

## 步骤 3：执行

```
/opsx:apply <序号>-<变更名>
```

**调用技能：** `openspec-apply-change`（通过 `/opsx:apply` 触发）

执行规则：

- 读取 `proposal.md`、`tasks.md` 全部上下文。
- 逐条实现 `tasks.md` 任务，每完成一条将 `- [ ]` 改为 `- [x]`。
- **每完成一条任务**：用该任务的**中文 commit 说明**将功能代码提交到本地仓库（一任务一 commit），再进入下一条。
- 无子代理双阶段审查链，适合低风险改动；遇歧义或设计问题须暂停等待指导。

**暂停条件：** 任务描述不清、发现需架构决策、遇到阻塞或错误无法自行解决。

---

## 步骤 4：归档

```
/opsx:archive <序号>-<变更名>
```

**调用技能：** `openspec-archive-change`（通过 `/opsx:archive` 触发）

将已完成变更从 `openspec/changes/<序号>-<变更名>/` 移至 `openspec/changes/archive/YYYY-MM-DD-<序号>-<变更名>/`。

归档后，当前轻量开发流程结束。归档目录同样不放入 `.gitignore`。

## 与流程 02 对比

| 维度 | 流程 02（Superpowers 质量） | 流程 05（OpenSpec 轻量） |
|------|----------------------------|-------------------------|
| 主体系 | Superpowers | OpenSpec |
| 设计文档 | `superpowers/.../design.md` | `proposal.md` |
| 执行依据 | `superpowers/.../plan.md` | `openspec/.../tasks.md` |
| 执行方式 | `subagent-driven-development` 或 `executing-plans` | `/opsx:apply` |
| 逐任务本地提交（中文 commit） | 强制，审查通过后一任务一 commit | 强制，每完成一条 tasks 一 commit |
| TDD + 双阶段审查 | 有 | 无 |
| 复审报告 | 必填 `review.md` | 可选 |
| 完成分支收尾 | 有（`finishing-a-development-branch`） | 无（用户自行合并 / PR） |
| 归档位置 | `superpowers/changes/archive/<序号>-<变更名>-YYYY-MM-DD/` | `openspec/changes/archive/YYYY-MM-DD-<序号>-<变更名>/` |
| 适用规模 | 中大型 | 小型 |

## 执行中发现问题时的处理

**核心原则：** 轻量流程不能硬扛复杂问题。若已超出本流程适用范围，必须升级到流程 02。

### 升级判断

立即停止 `/opsx:apply`，改走流程 02，当出现以下任一情况：

- 需跨多模块改动
- 需架构或技术方案决策
- 涉及安全、权限、金额、数据库 schema、核心业务状态机
- 任务数或文件数明显超出「小改动」预期
- 需要 TDD 与正式代码审查门禁

### 升级流程

```
/opsx:apply 执行中发现问题
    ↓
① 立即暂停轻量执行
    ↓
② 在 openspec/changes/<序号>-<变更名>/tasks.md 记录阻塞原因
    ↓
③ 判断是否超出轻量范围
    ↓
④ 若超出：转入流程 02，重新走 brainstorming → 分支检查 → writing-plans
    ↓
⑤ 若未超出：澄清 tasks.md 后继续 /opsx:apply
```

### 禁止事项

- ❌ 发现复杂设计问题后继续硬写 `tasks.md`（应升级到流程 02）
- ❌ 为本流程同时创建 `superpowers/changes/plan.md`（应只用 `tasks.md`）
- ❌ 多个小任务合并为一个 commit
- ❌ 使用英文撰写 commit 描述
- ❌ 未经用户明确要求就 `git push` 到远程
- ❌ 将 `openspec/changes/` 加入 `.gitignore`
- ❌ 逐任务功能代码 commit 时 `git add` AI 文档
- ❌ 未经用户要求擅自 commit AI 文档
