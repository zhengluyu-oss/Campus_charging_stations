# 流程 02：开发新功能

**目标：** 从需求到上线，兼顾质量与效率，避免重复文档。

**前置：** 先阅读 [文档管理规范.md](文档管理规范.md)。

**效率原则：** 用风险决定流程重量。高风险改动走完整质量门禁；低风险改动走轻量路径；任何路径都禁止维护两套设计、两套任务清单或两套归档。

---

## 路径选择（先做这一步）


| 条件                                      | 推荐路径          | 说明                              |
| --------------------------------------- | ------------- | ------------------------------- |
| 跨多模块 / 有架构决策 / 涉及安全、权限、金额、数据库、核心业务状态 | **路径 A：质量流程** | Superpowers 全链路：设计、当前分支确认、计划、执行、审查、验证、收尾 |
| 改动 ≤ 3 个文件 / 逻辑清晰 / 无架构决策 / 回滚容易       | **路径 B：轻量流程** | OpenSpec 快速记账并执行                 |


不确定时默认走路径 A。

---

## 路径 A：质量流程

**定位：** 中大型功能、跨模块改动、架构决策、需要 TDD 和审查的开发流程。  
**核心原则：** 路径 A 不使用 OpenSpec。Superpowers 是唯一的设计、计划、执行、审查与归档体系，避免两套 `tasks.md` 或两套归档记录。

**分支原则：** 开发开始前，用户已经手动创建并切换到新功能分支。AI 只在当前分支落代码，禁止自动创建新分支、切换分支或创建 git worktree；除非用户明确要求。

**目录命名（进行中与归档必须一致，日期只在末尾）：**

| 阶段 | 目录路径 | 示例 |
|------|----------|------|
| 进行中 | `superpowers/changes/<序号>-<变更名>/` | `superpowers/changes/6-add-station-overview/` |
| 已归档 | `superpowers/changes/archive/<序号>-<变更名>-YYYY-MM-DD/` | `superpowers/changes/archive/6-add-station-overview-2026-07-03/` |

命名规则：

- **序号必填**：`<序号>` 从 1 起全局递增，不重复，归档后保留不回收。
- **基础名一致**：进行中与归档使用相同的基础名 `<序号>-<变更名>`；归档仅在末尾追加 `-YYYY-MM-DD`（归档日）。
- **禁止日期前缀**：不得使用 `YYYY-MM-DD-<序号>-<变更名>` 等日期在前格式。
- **描述部分**：kebab-case 英文，禁止中文、空格或无意义名称。

**Git 规则：** AI 生成的 Superpowers 文档（`design.md`、`plan.md`、`review.md`、`fix-plan.md` 等）仅用于本地开发追溯，**禁止提交到 git**。`superpowers/changes/` 已在 `.gitignore` 中；提交代码时只包含功能代码，不得 `git add` 上述 AI 文档。

**执行依据：** `superpowers/changes/<序号>-<变更名>/plan.md`。

```
① brainstorming                    → design.md
② 当前分支检查 + 基线验证          → 确认不在 main/master，记录当前分支
③ writing-plans                    → plan.md
④ subagent-driven-development      → 按 plan.md 执行（推荐，内含逐任务审查）
   或 executing-plans               → 当前会话内执行（备选）
⑤ requesting-code-review           → 终审 review.md（按需补充，不重复内置审查）
⑥ receiving-code-review            → 验证并处理审查反馈（如有）
⑦ verification-before-completion   → 完成声明前证据门禁
⑧ finishing-a-development-branch   → 最终测试 + 合并 / PR / 保留 / 丢弃
⑨ Superpowers 归档                 → 归档本次设计、计划、审查记录
```

设计或计划变更：暂停执行，回到 `brainstorming` 或 `writing-plans` 更新 Superpowers 文档后再继续。

---

### A-1 设计与批准

**调用技能：** `brainstorming`（AI 自动）

描述目标："开发 `<序号>-<变更名>` 功能，分析需求和技术方案，不要写代码。"

**产出（唯一设计主文档）：**

```
superpowers/changes/<序号>-<变更名>/design.md
```

内容：需求、方案对比、设计决策、验收标准。你批准前禁止写代码。

---

### A-2 确认当前开发分支

**调用方式：** 普通 git 状态检查（不是 `using-git-worktrees`）

作用：

- 确认当前分支不是 `main` / `master` / 受保护发布分支。
- 记录当前分支名，后续所有改动都落在这个分支。
- 检查工作区是否存在未提交改动；如果有，区分用户已有改动和本次即将改动的范围。
- 禁止自动创建新分支、切换分支、创建 worktree 或清理 worktree。
- 安装依赖并运行基线测试，确认开发前状态可用。
- 如果基线测试失败，必须报告失败并询问是否继续，不能把旧失败当成新功能问题。

---

### A-3 编写实施计划

**调用技能：** `writing-plans`（在当前开发分支中执行）

**产出（唯一执行主文档）：**

```
superpowers/changes/<序号>-<变更名>/plan.md
```

要求：

- `plan.md` 使用 checkbox 任务清单，作为唯一任务进度来源。
- 每个任务包含精确文件路径、测试方式、预期输出和提交建议。
- 禁止再同步一份 OpenSpec `tasks.md`，避免两个任务清单不一致。
- 如果计划覆盖多个独立子系统，先拆成多个 plan，禁止把超大任务塞进一个计划。

---

### A-4 执行开发（推荐）

**调用技能：** `subagent-driven-development`（AI 自动）

执行规则：

- 主控制会话读取 `plan.md`，抽取任务并创建当前会话的执行清单。
- 每个任务派遣一个新的实现子代理，子代理按 TDD 完成实现和自检。
- 每个任务完成后必须经过两阶段审查：规格符合性审查 → 代码质量审查。
- 审查未通过时，必须修复并重新审查，不能直接进入下一个任务。
- 任务完成进度以 `plan.md` 的 checkbox 和当前会话任务状态为准。
- 全部任务完成后，必须有一次覆盖整个实现范围的最终审查。

**备选技能：** `executing-plans`

当任务耦合度较高、子代理不可用，或你明确要求当前会话逐步执行时，使用 `executing-plans`。它仍然读取同一个 `plan.md`，但由当前会话按批次执行并设置检查点。

使用 `executing-plans` 时必须补足质量门禁：

- 开始前批判性审查 `plan.md`，有疑问先暂停确认。
- 每完成约 3 个任务或一个完整批次，调用 `requesting-code-review` 做批次审查。
- Critical 和 Important 问题未解决前，不进入下一批。

---

### A-5 代码复审

**调用技能：** `requesting-code-review`（按门禁触发）

触发规则：

- 使用 `subagent-driven-development` 时：逐任务审查已内置，A-5 只确认最终审查是否已经覆盖完整实现范围；如果没有最终审查，再调用 `requesting-code-review` 补齐。
- 使用 `executing-plans` 时：每个批次后做批次审查，全部完成后再做一次最终审查。
- 不允许为了形式重复审查同一份 diff；也不允许因为已经做过局部审查而跳过最终整体审查。

**产出：**

```
superpowers/changes/<序号>-<变更名>/review.md
```

**复审结果处理：**

| 情况 | 处理方式 |
|------|----------|
| 无问题 | 进入 A-6 完成前验证 |
| 发现问题 | 执行下方"问题修复流程" |

---

#### 问题修复流程

```
代码复审发现问题
    ↓
① 生成问题报告：在 review.md 中记录所有问题（Critical/Important/Minor）
    ↓
② 暂停：等待用户审阅 review.md
    ↓
③ 用户审阅后，生成修复计划：创建 fix-plan.md
    ↓
④ 等待用户批准修复计划
    ↓
⑤ 用户说"允许修改"后，执行修复
    ↓
⑥ 修复完成后，重新进行代码复审（回到 A-5 开始）
    ↓
⑦ 复审通过 → 进入 A-6 完成前验证
```

**产出文件：**

```
superpowers/changes/<序号>-<变更名>/
├─ review.md      ← 问题报告
└─ fix-plan.md    ← 修复计划（单独文件）
```

**禁止事项：**

- ❌ 未生成问题报告直接修复
- ❌ 未等用户审阅就开始修复
- ❌ 未获用户批准就执行修改
- ❌ 修复后跳过重新复审

---

### A-6 完成前验证

**调用技能：** `verification-before-completion`

作用：给"实现完成、测试通过、可以收尾"这些结论提供新鲜证据。

在声称"完成"之前必须运行验证命令，并记录实际结果。推荐按风险选择验证矩阵：

- 后端单元测试 / 集成测试
- 前端构建 / 类型检查 / lint
- 关键业务路径的手动验证
- 数据库迁移或脚本的可执行性验证

规则：

- 验证命令必须是新鲜运行的，不能引用很久以前的结果。
- 只跑 lint 不能证明构建成功；只跑单测不能证明端到端业务可用。
- 如果某项验证因环境缺失无法执行，必须写清楚缺失原因和剩余风险。
- 没有实际验证输出，不允许声明开发完成。

---

### A-7 完成开发分支

**调用技能：** `finishing-a-development-branch`

完成前验证通过后，AI 必须进入当前分支收尾流程。该技能会再次确认测试状态，但本项目流程对它做如下约束：

- 不创建新分支。
- 不切换到其他分支，除非用户选择合并并明确确认。
- 不清理 worktree，因为本流程默认不创建 worktree。
- 不删除当前分支，除非用户明确要求丢弃并二次确认。

收尾选项：

```
1. 合并到主分支（本地）
2. 推送并创建 Pull Request
3. 保留分支（之后手动处理）
4. 丢弃本次分支工作
```

用户选择后再执行对应动作。涉及合并、推送、删除当前分支或丢弃本次改动等操作时必须二次确认。

如果 A-6 已经执行过完整测试，A-7 不重复跑所有无关检查；只按 `finishing-a-development-branch` 要求运行合并 / PR 前必要的最终验证。

---

### A-8 归档 Superpowers 记录

完成代码收尾后，归档本次 Superpowers 变更文档。归档时**保持与进行中相同的基础名**，仅在末尾追加归档日期：

```
进行中：superpowers/changes/<序号>-<变更名>/
   ↓ 移动至
归档：  superpowers/changes/archive/<序号>-<变更名>-YYYY-MM-DD/
```

示例：`superpowers/changes/6-add-station-overview/` → `superpowers/changes/archive/6-add-station-overview-2026-07-03/`

如果当前 Superpowers 工具提供归档命令，优先使用工具；如果没有可用命令，则按上方目录规范移动文档。归档对象至少包含：

- `design.md`
- `plan.md`
- `review.md`
- `fix-plan.md`（如有）

归档后，当前开发流程结束。归档目录同样受 `.gitignore` 约束，不得提交。

---

产出文件路径规范见 [文档管理规范.md](文档管理规范.md) 第 3.3–3.4 节。

## 路径 B：轻量流程

**适用：** 小改动。OpenSpec 既记账又执行，可省略 `superpowers/changes/`。

```
① /opsx:propose <序号>-<变更名>
② /opsx:apply <序号>-<变更名>
③ /opsx:archive <序号>-<变更名>
```

---

### B-1 创建变更

```
/opsx:propose <序号>-<变更名>
```

产出 `proposal.md` + `tasks.md`。`tasks.md` 即为执行清单。

---

### B-2 执行

```
/opsx:apply <序号>-<变更名>
```

读取 `tasks.md` 逐条实现并打钩。无子代理审查链，适合低风险改动。

---

### B-3 归档

```
/opsx:archive <序号>-<变更名>
```

---

## 两条路径对比


| 维度          | 路径 A（质量）                                            | 路径 B（轻量）        |
| ----------- | --------------------------------------------------- | --------------- |
| 主体系         | Superpowers                                         | OpenSpec        |
| 设计文档        | `superpowers/.../design.md`                         | 仅 `proposal.md` 或简短说明 |
| 执行依据        | `superpowers/.../plan.md`                           | `openspec/.../tasks.md` |
| 执行技能        | `subagent-driven-development` 或 `executing-plans` | `/opsx:apply`   |
| TDD + 双阶段审查 | 有                                                   | 无               |
| 复审报告        | 必填 `superpowers/.../review.md`                    | 可选              |
| 分支 / 工作区策略   | 使用用户当前已创建的新功能分支；不自动创建分支或 worktree             | 使用当前分支           |
| 完成分支        | 有，使用受约束的 `finishing-a-development-branch`      | 无               |
| 归档位置        | Superpowers 变更记录归档                              | `openspec/changes/archive/` |
| 适用规模        | 中大型                                                 | 小型              |

## 执行中发现问题时的处理

**适用场景：** 在 A-4 执行开发（或 B-2 执行）过程中，发现计划、设计或轻量任务描述存在问题。

**核心原则：** 文档是"决策快照"，不是"事后总结"。如果执行中发现问题，必须暂停并回到设计阶段重新规划，禁止默默修改计划继续执行。

路径 B 如果发现问题已经超出轻量范围，应立即停止 `/opsx:apply`，升级到路径 A；不要继续把复杂问题塞进 `tasks.md`。

---

### 问题类型与处理方式


| 问题类型      | 处理方式               |
| --------- | ------------------ |
| 技术方案不可行   | 暂停执行 → 回到 A-1 重新设计 |
| 需求理解有偏差   | 暂停执行 → 回到 A-1 重新设计 |
| 依赖不存在     | 暂停执行 → 回到 A-1 重新设计 |
| 发现更好的实现方式 | 暂停执行 → 回到 A-1 重新设计 |
| 任务拆分不合理   | 暂停执行 → 回到 A-3 重新规划 |


---

### 路径 A 处理流程

```
执行中发现问题
    ↓
① 立即暂停执行（不要继续按错误计划开发）
    ↓
② 记录问题：在 superpowers/changes/<序号>-<变更名>/plan.md 或 fix-plan.md 中说明发现的问题
    ↓
③ 回到设计阶段：重新调用 brainstorming 更新 design.md
    ↓
④ 更新计划：重新调用 writing-plans 更新 plan.md
    ↓
⑤ 重新确认 plan.md：确保任务拆分、测试命令、执行顺序与新设计一致
    ↓
⑥ 继续执行：从断点处继续
```

### 路径 B 升级流程

```
/opsx:apply 执行中发现问题
    ↓
① 立即暂停轻量执行
    ↓
② 在 openspec/changes/<序号>-<变更名>/tasks.md 记录阻塞原因
    ↓
③ 判断是否超出轻量范围
    ↓
④ 若超出：转入路径 A，重新走 brainstorming → 当前分支检查 → writing-plans
    ↓
⑤ 若未超出：澄清 tasks.md 后继续 /opsx:apply
```

---

### 禁止事项

- ❌ 默默修改 plan.md 继续执行（会导致文档与代码不一致）
- ❌ 路径 B 发现复杂设计问题后继续硬写 tasks.md（应升级到路径 A）
- ❌ 跳过设计阶段直接修改代码（会导致决策无法追溯）
- ❌ 不记录问题原因（会导致后续维护者无法理解决策过程）

---

### 示例场景

**场景：** 执行 A-4 时发现 `design.md` 中选择的第三方库不存在

**正确处理：**

1. 暂停 subagent-driven-development
2. 在 `plan.md` 或 `fix-plan.md` 记录：`发现 xxx 库不存在，需要重新选择方案`
3. 调用 brainstorming 重新分析技术方案
4. 更新 design.md 和 plan.md
5. 重新确认 plan.md 与新方案一致
6. 继续执行

**错误处理：**

- 直接换一个库继续开发（文档与代码不一致）
- 不记录问题，直接修改计划（决策无法追溯）
