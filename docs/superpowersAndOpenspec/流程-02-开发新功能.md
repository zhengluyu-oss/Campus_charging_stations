# 流程 02：开发新功能

**目标：** 从需求到上线，兼顾质量与效率，避免重复文档。

**前置：** 先阅读 [文档管理规范.md](文档管理规范.md)。

---

## 路径选择（先做这一步）

| 条件 | 推荐路径 | 说明 |
|------|---------|------|
| 跨多模块 / 有架构决策 / 需要 TDD 与审查 | **路径 A：质量流程** | Superpowers 执行 + OpenSpec 记账 |
| 改动 ≤ 3 个文件 / 逻辑清晰 / 风险低 | **路径 B：轻量流程** | OpenSpec 全程执行 |

不确定时默认走路径 A。

---

## 路径 A：质量流程

**分工：** Superpowers 负责设计与执行；OpenSpec 负责变更账本与归档。  
**执行依据：** `superpowers/changes/<序号>-<变更名>/plan.md`（不是 OpenSpec 的 tasks.md）。

```
① brainstorming          → design.md
② /opsx:propose          → 变更账本（proposal + tasks 从 design 派生）
③ writing-plans          → plan.md（并同步 tasks.md）
④ subagent-driven-development（读 plan.md，打钩 tasks.md）
⑤ requesting-code-review → review.md
⑥ /opsx:archive
```

设计变更（可选）：`/opsx:explore <序号>-<变更名>` → 更新 `design.md` / `plan.md` / `tasks.md`。

---

### A-1 设计与批准

**调用技能：** `brainstorming`（AI 自动）

描述目标："开发 `<序号>-<变更名>` 功能，分析需求和技术方案，不要写代码。"

**产出（唯一设计主文档）：**
```
superpowers/changes/<序号>-<变更名>/design.md
```

内容：需求、方案对比、设计决策、验收标准。你批准前禁止写代码。

---

### A-2 建立变更账本

**调用技能：** `openspec-propose`

```
/opsx:propose <序号>-<变更名>
```

从 `design.md` **派生**，不重复写一份完整设计：

```
openspec/changes/<序号>-<变更名>/
├─ proposal.md    ← 摘要：为什么做、影响范围
└─ tasks.md       ← 任务勾选清单（待与 plan 对齐）
```

---

### A-3 编写实施计划

**调用技能：** `writing-plans`（brainstorming 批准后自动衔接）

**产出（唯一执行主文档）：**
```
superpowers/changes/<序号>-<变更名>/plan.md
```

同时：将 `plan.md` 中的任务项同步到 `openspec/changes/<序号>-<变更名>/tasks.md`（一一对应，禁止两套不同任务）。

---

### A-4 执行开发

**调用技能：** `subagent-driven-development`（AI 自动）

- 读取：`superpowers/changes/<序号>-<变更名>/plan.md`
- 每完成一项：在 `openspec/changes/<序号>-<变更名>/tasks.md` 打钩 `- [x]`
- 内含：TDD、规格审查、质量审查

---

### A-5 代码复审

**调用技能：** `requesting-code-review`（AI 自动）

描述目标："任务已完成，进行代码复审。"

**产出：**
```
openspec/changes/<序号>-<变更名>/review.md
```

按 Critical → Important → Minor 处理反馈（`receiving-code-review`）。

---

### A-6 归档

```
/opsx:archive <序号>-<变更名>
```

归档至 `openspec/changes/archive/YYYY-MM-DD-<序号>-<变更名>/`。

---

产出文件路径规范见 [文档管理规范.md](文档管理规范.md) 第 3.3、3.4 节。

---

## 路径 B：轻量流程

**适用：** 小改动。OpenSpec 既记账又执行，可省略 `superpowers/changes/`。

```
① /opsx:propose <序号>-<变更名>
② /opsx:apply <序号>-<变更名>
③ /opsx:archive <序号>-<变更名>
```

---

### B-1 创建变更

```
/opsx:propose <序号>-<变更名>
```

产出 `proposal.md` + `tasks.md`。`tasks.md` 即为执行清单。

---

### B-2 执行

```
/opsx:apply <序号>-<变更名>
```

读取 `tasks.md` 逐条实现并打钩。无子代理审查链，适合低风险改动。

---

### B-3 归档

```
/opsx:archive <序号>-<变更名>
```

---

## 两条路径对比

| 维度 | 路径 A（质量） | 路径 B（轻量） |
|------|---------------|---------------|
| 设计文档 | `superpowers/.../design.md` | 仅 `proposal.md` |
| 执行依据 | `plan.md` | `tasks.md` |
| 执行技能 | `subagent-driven-development` | `/opsx:apply` |
| TDD + 双阶段审查 | 有 | 无 |
| 复审报告 | 必填 `review.md` | 可选 |
| 隔离工作区 | 无（直接在当前分支开发） | 无 |
| 完成分支 | 无（归档后即结束） | 无 |
| 适用规模 | 中大型 | 小型 |

## 执行中发现问题时的处理

**适用场景：** 在 A-4 执行开发（或 B-2 执行）过程中，发现计划或设计存在问题。

**核心原则：** 文档是"决策快照"，不是"事后总结"。如果执行中发现问题，必须暂停并回到设计阶段重新规划，禁止默默修改计划继续执行。

---

### 问题类型与处理方式

| 问题类型 | 处理方式 |
|---------|---------|
| 技术方案不可行 | 暂停执行 → 回到 A-1 重新设计 |
| 需求理解有偏差 | 暂停执行 → 回到 A-1 重新设计 |
| 依赖不存在 | 暂停执行 → 回到 A-1 重新设计 |
| 发现更好的实现方式 | 暂停执行 → 回到 A-1 重新设计 |
| 任务拆分不合理 | 暂停执行 → 回到 A-3 重新规划 |

---

### 处理流程

```
执行中发现问题
    ↓
① 立即暂停执行（不要继续按错误计划开发）
    ↓
② 记录问题：在 openspec/changes/<序号>-<变更名>/tasks.md 添加注释说明发现的问题
    ↓
③ 回到设计阶段：重新调用 brainstorming 更新 design.md
    ↓
④ 更新计划：重新调用 writing-plans 更新 plan.md
    ↓
⑤ 同步 tasks.md：确保 tasks.md 与新的 plan.md 对齐
    ↓
⑥ 继续执行：从断点处继续
```

---

### 禁止事项

- ❌ 默默修改 plan.md 继续执行（会导致文档与代码不一致）
- ❌ 跳过设计阶段直接修改代码（会导致决策无法追溯）
- ❌ 不记录问题原因（会导致后续维护者无法理解决策过程）

---

### 示例场景

**场景：** 执行 A-4 时发现 `design.md` 中选择的第三方库不存在

**正确处理：**
1. 暂停 subagent-driven-development
2. 在 tasks.md 添加注释：`<!-- 发现 xxx 库不存在，需要重新选择方案 -->`
3. 调用 brainstorming 重新分析技术方案
4. 更新 design.md 和 plan.md
5. 同步 tasks.md
6. 继续执行

**错误处理：**
- 直接换一个库继续开发（文档与代码不一致）
- 不记录问题，直接修改计划（决策无法追溯）
