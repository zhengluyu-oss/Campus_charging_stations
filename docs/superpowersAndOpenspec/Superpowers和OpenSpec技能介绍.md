# Superpowers 与 OpenSpec 技能全览

> 直接基于各 SKILL.md 文件整理，描述每个技能的真实作用和使用方式。

---

## 一、如何使用这些技能

**Superpowers 技能**（`brainstorming`、`writing-plans` 等）不是命令。你用自然语言描述目标，AI 判断应使用哪个技能，自动读取对应 SKILL.md 文件，按照其规定的流程执行。

**OpenSpec 技能**（`openspec-propose`、`openspec-apply-change` 等）有专属斜杠命令，你直接输入命令触发。

---

## 二、Superpowers 技能列表

---

### `using-superpowers` — 技能入口检查

**作用：** 确保每次对话开始时，AI 先检查是否有相关技能需要使用，是所有技能的总调度员。

**规则：** AI 只要有 1% 的可能性认为某个技能适用，就必须使用那个技能。

---

### `brainstorming` — 需求探索与设计

**作用：** 在写任何代码之前，先通过对话澄清需求、分析方案、形成设计文档。所有创作工作的强制第一步。

**执行流程：**
1. 扫描项目现有代码和文档，了解上下文
2. 如涉及视觉设计，询问是否需要可视化辅助
3. 一次一个问题，逐步澄清需求和约束
4. 提出 2-3 种实现方案，含对比和推荐理由
5. 逐节展示设计内容，每节等你确认
6. 你批准后，将设计写入文件并提交 git
7. 自检设计文档（查找 TBD、矛盾、歧义，直接修复）
8. 请你复审设计文档
9. 你批准后，自动衔接调用 `writing-plans`

**产出文件：**
```
superpowers/changes/<序号>-<变更名>/design.md   （功能 / 重构）
superpowers/changes/<序号>-<变更名>/diagnosis.md（Bug 修复）
superpowers/project/<固定文件名>.md       （接手项目）
superpowers/audit/<固定文件名>.md         （代码审计）
```

**硬性规则：** 设计文档未经你批准之前，禁止生成任何代码。

---

### `writing-plans` — 编写实施计划

**作用：** 将设计文档转换为可逐步执行的详细任务清单。每个步骤包含精确文件路径、具体代码、测试命令和预期输出。

**触发方式：** 由 `brainstorming` 在你批准设计文档后自动调用。

**产出文件：**
```
superpowers/changes/<序号>-<变更名>/plan.md
```

**计划特点：**
- 每个步骤 2-5 分钟可完成
- 每步都有具体代码，禁止出现"TBD"或"待补充"
- 遵循 TDD（先写测试，再写实现）
- 完成后询问你选择执行方式：子代理驱动（推荐）或内联执行

---

### `subagent-driven-development` — 子代理驱动开发（推荐）

**作用：** 为每个任务派遣独立的新鲜子代理执行，每个任务完成后进行两阶段审查（规格符合性 → 代码质量），持续执行直到所有任务完成。

**触发方式：** `writing-plans` 完成后，你选择"子代理驱动"执行方式时调用。

**每个任务的内部流程：**
1. 派遣实现子代理 → 按 TDD 实现代码，自检后提交
2. 派遣规格审查子代理 → 确认代码符合设计规格
3. 有缺口则修复，再次审查（循环直到通过）
4. 派遣代码质量审查子代理 → 检查代码质量
5. 有问题则修复，再次审查（循环直到通过）
6. 标记任务完成，进入下一个任务
7. 全部任务完成后，派遣最终代码审查子代理
8. 自动调用 `finishing-a-development-branch`

---

### `executing-plans` — 内联执行计划

**作用：** 在当前会话中直接逐步执行计划，适合没有子代理支持的平台。

**触发方式：** `writing-plans` 完成后，你选择"内联执行"时调用。

**流程：**
1. 读取计划文件，批判性审查，有疑虑先提出
2. 按步骤逐个完成任务，遇到阻塞立即停止等待指导
3. 全部完成后调用 `finishing-a-development-branch`

---

### `finishing-a-development-branch` — 完成开发分支

**作用：** 实现完成后，验证测试通过，然后提供结构化选项处理分支。

**触发方式：** 由执行类技能（`subagent-driven-development` 或 `executing-plans`）在所有任务完成后自动调用。

**流程：**
1. 运行测试套件（失败则停止，不继续）
2. 检测工作区状态
3. 展示选项：
   ```
   1. 合并到主分支（本地）
   2. 推送并创建 Pull Request
   3. 保留分支（之后手动处理）
   4. 丢弃这个分支
   ```

---

### `using-git-worktrees` — 创建隔离工作区

**作用：** 在独立的 git worktree 中进行开发，避免影响当前分支。

**触发方式：** 开始执行开发计划之前，AI 自动调用。

**流程：**
1. 检测是否已在隔离工作区（已在则跳过）
2. 优先使用平台原生工具；否则手动创建 git worktree
3. 验证工作区目录已在 `.gitignore` 中（否则先添加）
4. 运行项目依赖安装命令
5. 运行测试确认基线干净后继续

**默认工作区路径：** `.worktrees/<分支名>/`

---

### `requesting-code-review` — 发起代码审查

**作用：** 派遣专门的代码审查子代理，对已完成的工作进行全面审查，输出结构化反馈报告。

**触发方式：** 功能实现完成后，AI 自动调用（或你主动说"做代码复审"）。

**流程：**
1. 获取本次变更的 git commit 范围
2. 派遣代码审查子代理，提供功能描述、计划文档、commit 范围
3. 审查子代理返回结构化报告
4. 按优先级处理反馈：Critical → Important → Minor

---

### `receiving-code-review` — 处理代码审查反馈

**作用：** 确保收到审查反馈后，进行技术验证再实现，而不是盲目同意或表演性地表示认可。

**触发方式：** 收到代码审查反馈时自动调用。

**核心规则：**
- 禁止表演性同意（"你完全正确！"等）
- 先理解，再验证，再实现
- 有不清楚的地方先澄清，不猜测就实现
- 外部审查建议先验证是否适用于当前代码库

---

### `systematic-debugging` — 系统性调试

**作用：** 遇到任何 Bug、测试失败、意外行为时，强制先找根本原因，再提出修复方案。禁止猜测修复。

**触发方式：** 遇到任何技术问题时自动调用。

**四个阶段（必须按顺序完成）：**

| 阶段 | 内容 |
|------|------|
| 1. 根本原因调查 | 读错误信息、复现问题、检查最近变更、追踪数据流 |
| 2. 模式分析 | 找到能正常工作的相似代码，对比差异 |
| 3. 假设与验证 | 提出单一假设，最小化验证，每次只改一处 |
| 4. 实现修复 | 先写失败测试，修复根因，验证通过 |

**铁律：** 未完成根本原因调查，不允许提出任何修复方案。尝试 3 次修复失败后，必须停下来质疑架构设计。

---

### `test-driven-development` — 测试驱动开发

**作用：** 强制要求先写失败测试，再写实现代码，遵循红绿重构循环。

**触发方式：** 子代理实现代码时自动使用。

**循环：**
1. 写最小化的失败测试
2. 确认测试确实失败（且是预期的失败方式）
3. 写最少的代码让测试通过
4. 确认所有测试通过
5. 重构清理（保持绿色）
6. 重复

**铁律：** 没有先失败的测试，禁止写任何生产代码。

---

### `verification-before-completion` — 完成前验证

**作用：** 在声称任何工作"完成了"或"通过了"之前，必须运行验证命令并展示实际输出作为证据。

**触发方式：** 即将声称任务完成时自动调用。

**铁律：** 没有验证命令的实际输出，不能声称任何事情完成了。

---

## 三、OpenSpec 技能列表

OpenSpec 是变更记录管理系统，通过 CLI 工具 `openspec` 管理每次代码变更的完整文档。

**前提：** 需要已安装 `openspec` CLI 工具。

**变更文件结构：**
```
openspec/changes/<序号>-<变更名>/
├─ proposal.md    # 为什么做这个变更（背景、目标）
├─ design.md      # 怎么做（设计决策、权衡）
├─ tasks.md       # 任务清单（- [ ] 待做，- [x] 已完成）
└─ specs/         # 详细规格（按功能模块）

openspec/changes/archive/YYYY-MM-DD-<序号>-<变更名>/   # 已完成变更归档
```

---

### `openspec-explore` — 探索模式

**命令：** `/opsx:explore` 或 `/opsx:explore <序号>-<变更名>`

**作用：** 进入只读探索状态，作为思维伙伴帮你探索想法、分析问题、澄清需求。可以读代码、画架构图、比较方案，但绝对不写任何应用代码。

**适用场景：**
- 动手之前把想法理清楚
- 开发中途遇到复杂问题需要重新思考
- 对现有代码某个模块有疑问

**可以做：**
- 提出自然涌现的澄清问题
- 调查代码库，找集成点和架构模式
- 比较多种方案，画对比表、ASCII 架构图
- 指出风险和未知项
- 如当前有 OpenSpec 变更：读取已有文档，提议更新某个部分

**不做：** 写任何应用代码

---

### `openspec-propose` — 创建变更提案

**命令：** `/opsx:propose <序号>-<变更名>`

**作用：** 通过 `openspec new change` 命令创建变更目录，然后按依赖顺序依次生成 `proposal.md`、`design.md`、`tasks.md`，让变更立即进入可实施状态。

**流程：**
1. 运行 `openspec new change "<序号>-<变更名>"` 创建目录
2. 运行 `openspec status --json` 获取需要生成的文档列表
3. 按依赖顺序逐个生成文档
4. 展示最终状态，提示可运行 `/opsx:apply` 开始实施

---

### `openspec-apply-change` — 执行变更任务

**命令：** `/opsx:apply` 或 `/opsx:apply <序号>-<变更名>`

**作用：** 读取变更记录中的 `tasks.md`，逐条实现任务，每完成一条立即将 `- [ ]` 改为 `- [x]`。

**流程：**
1. 确认要实施的变更（可从上下文推断或询问）
2. 读取 `proposal.md`、`design.md`、`tasks.md` 等全部上下文
3. 展示当前进度（已完成 N/M 个任务）
4. 逐条实现待完成任务
5. 遇到歧义或设计问题暂停，等待指导

**暂停条件：** 任务描述不清、发现设计问题、遇到错误或阻塞

---

### `openspec-archive-change` — 归档已完成变更

**命令：** `/opsx:archive` 或 `/opsx:archive <序号>-<变更名>`

**作用：** 将完成的变更从 `openspec/changes/` 移动到带日期前缀的归档目录，并检查是否需要同步 delta specs。

**流程：**
1. 确认要归档的变更（不会自动猜测，必须确认）
2. 检查文档是否全部完成（未完成则警告并确认）
3. 检查任务清单是否全部打钩（未完成则警告并确认）
4. 检查 delta specs 是否需要同步到主规格
5. 执行归档（移动目录，加日期前缀 `YYYY-MM-DD-<序号>-<变更名>`）

---

## 四、技能协作关系

```
Superpowers 开发主链：
brainstorming → writing-plans → using-git-worktrees
→ subagent-driven-development（内含 TDD + requesting-code-review）
→ finishing-a-development-branch

OpenSpec 变更记录链：
/opsx:explore（可选）→ /opsx:propose → /opsx:apply → /opsx:archive

仅分析，不改代码：
brainstorming 或 /opsx:explore

遇到 Bug：
systematic-debugging → TDD 修复 → verification-before-completion
```
