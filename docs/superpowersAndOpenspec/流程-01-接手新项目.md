# 流程 01：接手新项目，建立完整认知

**目标：** 在不改动任何代码的前提下，建立对项目架构、模块、业务流程、数据模型的**完整、可检索、可执行**认知。文档**不设字数上限**，宁可冗长也不要遗漏。

**不使用 OpenSpec**（此阶段只有分析，无代码变更）。

**前置：** 先阅读 [文档管理规范.md](文档管理规范.md)。

**核心原则：**
- **穷尽式采集**：能从代码、配置、SQL、注释、前端路由、接口注解中提取的信息，全部写入对应文档。
- **可验证**：每条关键结论标注信息来源（文件路径 + 行号或类名），便于后续核对。
- **数据库优先详尽**：`infrastructure.md` 的数据库章节须先写**全表整体介绍**（业务域、主链路、表依赖），再逐表、逐字段展开，并对照项目内已有数据库文档（如 `docs/数据库.md.md`）与 `schema.sql`，不得用「详见 schema.sql」代替。
- **禁止占位符**：不得出现「待补充」「TBD」「略」等未完成标记；确实无法确认时写「未在代码中找到，需人工确认」并说明已检索范围。

## 步骤 1：整体架构分析

**调用技能：** `brainstorming`（AI 自动）

**描述目标：**
> 帮我穷尽式分析这个项目的整体架构，不要修改任何代码。产出必须达到下方 `overview.md` 与 `architecture.md` 模板的每一项，不得省略。

### 1.1 产出：`superpowers/project/overview.md`

按以下章节**逐项填满**（无字数限制）：

#### 1. 项目基本信息
- 项目名称、仓库路径、业务领域一句话描述
- 目标用户（学生端 / 管理端 / 其他）
- 项目成熟度判断（原型 / 迭代中 / 生产可用）及依据

#### 2. 技术栈全景（含版本号）
对每一项写明：**名称 + 版本 + 用途 + 配置文件来源**

| 层级 | 必须列出的项 |
|------|-------------|
| 语言与运行时 | JDK、Node.js、Python 等 |
| 后端框架 | Spring Boot、MyBatis、安全框架等 |
| 前端框架 | Vue/React、UI 库、状态管理、构建工具 |
| 数据库与中间件 | MySQL、Redis、MQ、对象存储等 |
| 鉴权 | JWT / Session / OAuth 等 |
| 其他 | 定时任务、异步、WebSocket、文件上传等 |

#### 3. 仓库目录结构（完整树形）
- 从项目根目录展开**至少 3 层**（关键子目录可更深）
- 每个**一级目录**附一句话职责说明
- 标注：哪个是用户端前端、管理端前端、后端子模块、公共模块、文档、脚本

#### 4. 子项目 / 多模块说明
若有 monorepo 或多 Spring 模块，逐模块说明：
- 模块名、artifactId、启动类
- 监听端口（从 `application.yml` 读取）
- 模块间依赖关系（谁依赖 `common` 等）

#### 5. 本地启动手册（可逐步执行）
对每个可运行单元给出：
```text
前置条件（MySQL 已启动、Redis、环境变量等）
安装依赖命令
启动命令
访问地址（含端口）
默认账号（若有）
常见启动失败原因
```

#### 6. 环境变量与配置
- 列出 `.env.example` / `application-*.yml` 中**每一个**关键配置项
- 表格：配置键 | 默认值 | 含义 | 是否敏感 | 定义文件

#### 7. 外部依赖服务
- 数据库连接串格式、库名、字符集
- 第三方 API（支付、短信、OSS 等）：是否接入、代码位置

#### 8. 规模与复杂度粗估
- 后端 Controller / Service / Mapper 数量（可 `grep` 统计）
- 前端页面 / 组件数量
- 数据表数量
- 主要风险区域一句话列表（指向后续 `architecture.md` 展开）

#### 9. 文档与规范索引
- 项目内已有 `docs/`、`README` 清单及可信度说明
- 与 `superpowers/project/` 产出的关系（哪些是人工维护、哪些是 AI 接手产出）

- ASCII 或 Mermaid 总览图（客户端 → 网关/代理 → 后端模块 → DB/缓存）

| 层级 | 职责 | 代表性文件 |
|------|------|-----------|
| Controller | | |
| Service / ServiceImpl | | |
| DAO / Mapper | | |
| Entity / DTO / VO | | |
| Config / 拦截器 / 切面 | | |
| Common / 工具类 | | |

#### 3. 前端架构
- 用户端 vs 管理端：技术栈是否一致、代理配置差异
- 路由结构、布局组件、状态管理（Pinia/Vuex）存放位置
- API 封装方式（`request.ts` 拦截器、Token 注入、错误统一处理）

#### 4. 请求全链路（以一条典型业务为例）
逐步写出，例如「用户扫码开始充电」：
```text
浏览器 → 前端路由 → Vue 组件 → API 调用

```

- 后端子模块（`admin` / `user` / `common`）依赖关系

#### 6. 鉴权与权限架构
- 登录流程（注册/登录接口、密码加密方式、Token 生成与校验类）
- 用户端 vs 管理端：是否共用一套 JWT、请求头字段名
- 哪些接口免登录、哪些需角色（从拦截器/注解/配置归纳）
- Token 过期、刷新、登出策略

#### 7. 横切关注点
- 全局异常处理（类名、统一响应结构）
- 日志记录（是否写 `system_logs` 表、AOP 位置）
- 文件上传（存储路径、访问 URL 规则）
- 事务边界（哪些 Service 方法有 `@Transactional`）
- 异步任务（`@Async`、定时任务类）

#### 8. 数据流与状态同步
- 充电桩状态、订单状态在 DB / 内存 / 前端之间如何同步
- 是否有轮询、WebSocket、定时修正

#### 9. 已知架构风险与技术债
逐条列出：现象 | 影响 | 相关文件 | 严重度（高/中/低）

#### 10. 扩展点说明
- 新增一个业务模块应放在哪一层、参考哪个现有模块
- 新增一张表应改哪些文件（entity、mapper、migration）

## 完成标准

以下 **6 个文件全部存在**，且每个文件均达到上文模板的章节要求（无占位符、无「略」）：

```
superpowers/project/
├─ overview.md          # 步骤 1.1 — 项目全景与启动手册
├─ architecture.md      # 步骤 1.2 — 分层、链路、鉴权、风险
├─ modules.md           # 步骤 2.1 — 逐模块类与文件对照
├─ business-flow.md     # 步骤 2.2 — 逐业务流程与状态机
├─ api-system.md        # 步骤 2.3 — 全量接口清单
└─ infrastructure.md    # 步骤 3.1 — 数据库（全表整体介绍 + 逐表逐字段）+ 部署/缓存/日志/构建
```

### 自检清单（接手结束前逐项打勾）

- [ ] `overview.md` 含完整目录树、启动命令、配置项表
- [ ] `architecture.md` 含至少一条端到端请求链路与鉴权说明
- [ ] `modules.md` 每个业务域均有 Controller / Service / Mapper 列表
- [ ] `business-flow.md` 每个核心流程有步骤编号与状态机（如适用）
- [ ] `api-system.md` 接口数量与 Controller 扫描结果一致
- [ ] **`infrastructure.md` 数据库章节：在逐表详解之前有「数据表整体介绍」（业务域分组、主链路、表依赖层次）**
- [ ] **`infrastructure.md` 数据库章节：每张表均有完整字段表，字段数与 DDL 一致**
- [ ] **`infrastructure.md` 含 ER 图，并对照 `docs/数据库*.md` / schema.sql / Entity 列出差异**
- [ ] `infrastructure.md` 基础设施章节含端口表与构建命令
- [ ] 全部结论均标注来源文件，无未解释的「待补充」
